# セキュリティと公開前チェック

[English](security.md) · [README](../README.ja.md)

## リポジトリに入れないもの

- 実際のIPアドレスまたは内部ホスト名
- 実際のユーザー名
- パスワード、秘密鍵、API token
- 実際のローカルまたはリモートの絶対ディレクトリ
- `.ssh/config`、`.env`、接続ログ、画面キャプチャ

リポジトリ内の例には、予約済みの無効ドメインと説明用プレースホルダーだけを使います。実際の接続情報は、リポジトリ外にあるローカルのSSH configで管理します。

## 実行時の境界

`claudefws`は、マウントしたプロジェクトディレクトリを作業ディレクトリとし、permission modeを`auto`としてClaude Codeを起動します。`codexfws`は同じディレクトリで、`workspace-write`サンドボックスと`on-request`承認によりCodex CLIを起動します。対象は選択したプロジェクトディレクトリであり、リモートファイルシステム全体のマウントは拒否します。

`auto`モードは、安全と判定した操作を確認なしで承認します。したがって、すべてを確認する`manual`モードよりも副作用が発生する閾値は低くなります。これは、読み取り専用のリモートコマンドを多数実行するリモート作業向けの意図的な既定値です。作業内容に応じて、起動ごとにより厳しいモードを選べます。

```zsh
AFWS_PERMISSION_MODE=manual claudefws SSH_CONFIG_HOST REMOTE_ABSOLUTE_DIRECTORY
AFWS_PERMISSION_MODE=plan claudefws SSH_CONFIG_HOST REMOTE_ABSOLUTE_DIRECTORY
```

`bypassPermissions`は指定しないでください。セッション内のすべての書き込みはマウント越しにリモートへ到達するため、ローカルだけで済む影響範囲というものが存在しません。

ClaudeとCodexには次の方針がセッションごとに渡されます。

- マウントを唯一のプロジェクトcheckoutとしてファイル操作とGitに使い、利用者が明示的に求めない限りcloneやworktreeを作らない。
- ワークステーション環境が必要なプログラムだけを`afws-run`経由で実行する。
- リモートのパッケージ、シェル初期化ファイル、システムまたはユーザー環境を、明示的な承認なしに変更しない。
- 破壊的・高コスト・長時間の操作の前に確認する。
- リモートの排他資源を使う前に`afws-lock`で確保し、利用者の指示がない限り保持中のロックを奪わない。

SSHは設定されたリモートユーザーの権限で動作し、それを超える権限は取得しません。接続に使うユーザーの権限が大きいほど想定される影響も大きくなるため、必要最小限の権限のアカウントを使ってください。

`claudefws`は管理者権限を付与も模倣もしません。リモートのアカウントが`sudoers`等の仕組みで許可されていない場合、`sudo`のようなコマンドで権限を昇格させることはできず、失敗します。launcherは対話的なSSH TTYを確保せず、sudoのパスワードを保存・提供・転送することもありません。

アカウントの名目上のsudo可否だけでなく、実際の権限も確認してください。既存のサーバー設定によって、パスワードなしsudo、コンテナランタイムのグループなどの特権グループ、set-user-IDプログラム、サービス管理権限、書き込み可能な特権自動化処理を通じて、すでに昇格した権限が与えられている場合があります。実効的なセキュリティ境界は、そのリモートアカウントに割り当てられた権限の全体です。

`afws-run`は、設計上リモートコマンドの実行器です。マウント済みセッション内では、典型的なプロジェクト探索・ファイル操作・Gitコマンドを、`--allow-remote-files`が明示されていない限り拒否します。直接コマンドだけでなく、一般的なshell・標準入力スクリプト・ラッパーも静的に検査します。これは作業手順上のガードであり、セキュリティ境界ではありません。通常のプログラムはファイルを読み書きでき、間接的・動的なshellコードをすべて判定することもできません。指定したリモートディレクトリは開始位置にすぎません。承認の前にコマンドを確認してください。特に、そのディレクトリの外に出るもの、ファイルを削除するもの、パッケージを導入するもの、高コストなジョブを開始するもの、リモート環境を変更するものは注意が必要です。

## セッションレジストリが保持する情報

`~/.afws/sessions/`配下のレジストリは、動作中の各セッションについて、名前、種別、プロセスID、SSHの接続名、リモートディレクトリ、マウントポイントを記録します。所有者のみがアクセスできる権限で作成され、資格情報、ホスト鍵、接続の秘密情報は含みません。ただし、実際の接続名と実際のリモートパスは含みます。SSH configと同様に扱ってください。画面キャプチャ、ログ、課題報告に含めず、このリポジトリへコピーしないでください。

Codexでは信頼済みのライフサイクルフックが`~/.afws/session-meta/`にスレッドID、`busy`/`idle`、短い作業ラベルも所有者専用で保存します。未設定なら直近のユーザープロンプトの最初の行（最大160文字）がラベルになり、`afws-status set`で明示的なラベルを設定できます。ほかのローカルセッションの一覧へ秘密情報を出したくない場合、ラベルやプロンプトの最初の行に含めないでください。フックはモデルの文脈へ他セッション一覧を流しませんが、Codexのコマンドサンドボックス外で実行されるため、起動時の信頼確認では内容を確認してください。Codexエージェントが明示ラベルを書いたり`afws-message`から`codex queue`を呼ぶ際は、サンドボックスの承認が必要な場合があります。

`afws-lock`も同種の情報、すなわちセッション名、時刻、TTLを、リモート側の`~/.afws-locks`配下のロックディレクトリへ書き込みます。プロジェクトツリーの中には何も書き込まないため、ロックがプロジェクトのGit履歴へ入ることはありません。

## この構成が守るもの・守らないもの

エージェントをワークステーションではなくMacで動かすことには意味がありますが、何を得ているのかは正確に把握しておく価値があります。

**エージェントの状態をワークステーションに残さない効果はあります。** 認証情報、蓄積された許可ルール、セッション履歴、プラグインはMac側にあります。これは重要です。許可ルールは蓄積するもので、共有マシンでエージェントを直接使い続けると、誰も見直さない長い許可リストができ、それがそのマシンの以降の全セッションに効きます。エージェントのシェルがMac側にあるため、ワークステーション上に長時間残るプロセスを偶発的に置いていくこともありません。

**一方、それだけでエージェントの到達範囲が狭まるわけではありません。** それを決めるのは次の2つで、どちらも利用者が設定するものです。

- *何をマウントするか。* リモートのホームディレクトリをマウントすると、`~/.ssh`、他のすべてのプロジェクト、あらゆるdotfileがワークスペースの中に入ります。ホームではなくプロジェクトディレクトリをマウントしてください。
- *`afws-run`で何を実行できるか。* これはSSHユーザーとしての無制限なリモートシェルです。これを呼べるエージェントは、マウント範囲に関係なく、そのユーザーが読めるものをすべて読めます。それが成り立つ限り、マウントは利便性の境界であってセキュリティ境界ではありません。

ランチャーはこれを検知して警告します。ワークスペースに`.ssh`・`.claude`・`.codex`のいずれかがある場合、ホームディレクトリのように見えると報告し、プロジェクト設定として読み込まれる設定ファイルを名指しします。拒否ではなく警告です。どちらにしてもアカウントの権限が効くことは変わらないためです。`AFWS_ALLOW_HOME_MOUNT=1`で抑止できます。また`afws-doctor HOST`は、共有接続が既に開いている場合にワークステーション側のエージェント導入を検出して報告します。2か所に入っていることは、許可ルールとバージョンが2系統に分かれることを意味するためです。

**モデルに渡る情報が減るわけでもありません。** マウント経由で読んだファイルは、エージェントがワークステーション上で動いていた場合とまったく同じようにモデルへ渡ります。外部に出してはいけないデータがあるなら、そもそもマウントしないことが答えです。

実際に成立する境界はワークステーション側にあります。エージェント専用のSSH鍵を用意し、`authorized_keys`で`restrict`と`command=`の強制コマンドを指定して、シェルではなく小さなラッパー（ジョブ開始・停止・ログ取得）だけを実行させる構成です。そうすればMac側で判断を誤っても、ワークステーションがそれ以外を実行しないため、`~/.ssh`や他プロジェクトへは到達できません。このリポジトリはその設定を行いません。

## 共有SSH接続のソケット

`~/.afws/control/HOST.sock`は、認証済みで生きたリモートホストへの経路です。このソケットに到達できるものは、再認証なしにリモートユーザーとしてコマンドを実行できます。ディレクトリは所有者のみアクセス可能な権限で作成され、それが保護の境界になります。権限を緩めたり、共有ファイルシステム上へ置いたり、`AFWS_STATE_DIR`を他ユーザーから読める場所へ向けたりしないでください。

接続は`AFWS_CONTROL_PERSIST`秒（既定600秒）の無通信で自動的に失効します。対話型launcherには独立したwatchdogがあり、launcherが強制終了した場合も接続を閉じますが、両方の後片付けプロセスが停止した場合に備えて失効時間も残しています。`afws-umount --orphaned`は生存セッションが使っていない接続を閉じ、`afws-doctor`はそれを検出して報告します。

`AFWS_KEEP_CONTROL_MASTER=1`は、この2つの境界のうち前者を取り除きます。そのホストを使う最後のセッションが終了しても接続は閉じられず、失効するまで残ります。これは明確な緩和です。認証済みの経路が、それを必要としたすべてのセッションより長く生き残るため、その間ソケットに到達できるものはリモートユーザーとして振る舞えます。この設定が存在するのはパスワード認証のホストのためであり、そうしなければ起動のたび、そしてセッション外の`afws-run`のたびにパスワードを入力することになるからです。ホストごとに意図して設定し、`AFWS_CONTROL_PERSIST`は想定する作業時間を超えない値にとどめ、終わったら手動で接続を閉じてください。既定では無効です。

そのホストでの作業を終えたら接続を閉じます。

```zsh
ssh -S ~/.afws/control/HOST.sock -O exit HOST
```

## セッション間メッセージは入力であり、命令ではない

他のセッションからのメッセージは、利用者のために動いている別のセッションが書いた内容であり、信頼されたコマンド経路ではありません。データの削除、パッケージの導入、保持中ロックの奪取、自身の作業範囲の拡大などを求められた場合、受け取ったセッションは他の依頼と同様に扱い、まず自分の利用者に確認するべきです。セッション間メッセージは、実際に実行・観測した内容を交換するためのものです。

## GitHubへpushする前に

公開候補の内容に対してチェックを実行します。

```zsh
./scripts/test.sh
./scripts/prepublish-check.sh
git status --short
```

自動検査は保険であり、機密情報が存在しないことを保証するものではありません。commit前に全ファイルを確認し、`git diff --cached`も点検してください。

一度でも秘密情報をcommitした場合、後のcommitで削除してもGitの履歴からは消えません。その履歴をpushしないでください。まず履歴から取り除き、該当の資格情報を無効化または更新してください。

## これらのスクリプトが行わない操作

同梱のinstaller、doctor、testは、Git remoteの追加、commit、push、release作成を行いません。リポジトリの公開操作は、内容確認後に別途実施してください。
